# WI-011 Evidence｜Dynamic Add Project Backend API

Status: `READY_FOR_REVIEW`

## Acceptance target

GP-01 backend slice: add a local project root to a running localhost server, validate its identity, bootstrap it conservatively when needed, persist Dashboard registration, attach a watcher and expose it through `GET /api/projects`.

## Behavior evidence

| Scenario | Evidence |
| --- | --- |
| Existing `.ai-ledger` | Returns `kind=existing`, registers the project immediately, serves its snapshot, and leaves `tasks.json` unchanged. |
| Legacy Markdown | Returns `kind=migrated`, creates the machine ledger using existing migration code, reports LOW-confidence warnings without task titles, and preserves Markdown bytes. |
| Empty directory | Returns `kind=initialized`, creates the existing seven-file skeleton, registers the derived stable projectId and exposes it through the API list. |
| Project identity | Current ledger loading rejects a `project.json.rootPath` mismatch; active/registry duplicate IDs or roots on different folders return a safe conflict response. |
| Dynamic watcher | A watched `tasks.json` change after POST produces the existing `task:changed` SSE event for the newly registered project. |
| Error boundary | Invalid roots and invalid ledgers return generic stable messages without echoing supplied paths, ledger contents or secret-like values. |

## Safety boundaries

- Migration remains additive and uses the existing allowlisted Markdown detector/parser.
- Registration writes only the Dashboard registry configuration file.
- Existing task state is read-only during registration; no task status/progress/role/session state is written by the new API path.
- The server remains localhost-only and watcher implementation code was not modified.

R90 should independently rerun the gates and review the dynamic lifecycle, registry conflict behavior, safe error payloads and GP-01 integration. This evidence does not claim `VERIFIED` or `ACCEPTED`.
